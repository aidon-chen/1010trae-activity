# 本地抽奖服务与运行说明

实现日期：2026-10-10。保留现有转盘页面，增加本机 Node.js 服务；无需联网抽奖或安装数据库服务，无第三方 npm 运行依赖。

## 开源方案调研

| 方案 | 适用范围 | 此仓库的选择 |
| --- | --- | --- |
| [qiaomu-lucky](https://github.com/joeseesun/qiaomu-lucky) | 自托管抽奖、Node API、管理与记录导出 | 参考本地服务与记录管理的组织方式；此项目已有页面，不引入完整 React 应用 |
| [lucky-canvas](https://github.com/buuing/lucky-canvas) | Canvas 转盘、九宫格、异步抽奖，前后端控制结果 | 现有 Canvas 已满足动画需求，保留页面；库存和结果交给后端 |
| [moshang-ax/lottery](https://github.com/moshang-ax/lottery) | 年会人员名单、3D 展示和抽取结果导出 | 偏人员名单抽奖，与按库存发放礼物的活动模型不同 |

这是针对现有仓库编写的实现，没有复制上述项目代码。运行层使用 [Node.js SQLite](https://nodejs.org/download/release/v24.15.0/docs/api/sqlite.html) 与 [crypto.randomInt](https://nodejs.org/download/release/v24.15.0/docs/api/crypto.html#cryptorandomintmin-max-callback)。已在本机 Node.js 24.15.0 验证，内置 SQLite 在该版本处于 release candidate 阶段；本仓库固定要求 24.15 或更新的 24.x。

## 原实现的问题与调整

- 原奖池是单浏览器 localStorage，多个浏览器无法共享库存。现在同一台电脑上访问 localhost / 127.0.0.1 都共用 SQLite。
- 原缓存校验失败会重新生成满库存。现在数据库、库存或记录异常会报错并停止，不自动补签。
- 原先按名称记录结果，参数修改或重置会清空记录。现在每个奖池、奖项、请求和结果有独立编号；新建奖池会归档原奖池，CSV 包含全部历史。
- 原先在浏览器用 Math.random 洗牌。现在服务器使用随机整数按剩余数量抽取；扣库存与写记录处于同一 `BEGIN IMMEDIATE` 事务，写入失败全部回滚。
- 抽取接口使用请求编号去重，连接丢失时按同一编号重试。转盘动画只展示已提交的服务器结果。
- 数据库使用 WAL、FULL 同步；启动检查数据库与逐项库存/抽奖记录一致性。
- 启动、每 20 条新结果、新建奖池前及导入前保存数据库备份，也支持手工下载 SQLite 备份。备份存放在 `data/backups/`，不会自动删除。

随机结果不能提前从浏览器读取。这里不提供第三方可验证的随机证明，也不实现按身份限制“每人一次”；当前用途是由现场工作人员在本机操作。

## 启动、停止、后台运行

要求 Node.js 24.15+ 的 24.x 已加入 PATH。在仓库目录运行：

```powershell
# 常驻后台：关闭终端或 Codex 后仍运行，服务异常退出后自动重试
node scripts/service.cjs start
# 停止后台服务，保留数据
node scripts/service.cjs stop
# 请求守护进程结束自己的服务进程，并按异常退出恢复路径重新启动
node scripts/service.cjs restart
```

也可运行 `scripts/Start-Local.ps1` / `scripts/Stop-Local.ps1`。前台开发使用 `npm start` 或 `node server/index.cjs`，Ctrl+C 停止。后台与前台使用同一数据库，但不要同时占用 5173。修改服务代码后先停止再启动，网页代码修改后刷新。

打开 <http://127.0.0.1:5173/lucky-wheel.html>。主页和问答也由同一服务提供。所有脚本使用仓库绝对路径定位文件，不依赖启动时工作目录；服务绑定 `127.0.0.1`，不需要开放防火墙。

后台守护进程记录在 `data/service.json`，日志为 `data/service.log`。连续 8 次快速启动失败后停止重试，避免端口冲突或损坏数据库下无限启动。停止通过带实例编号的信号文件实现，不按一个未经确认的 PID 强制结束其他程序。

Windows 重启后需要再次运行启动命令；电脑休眠时服务暂停。此实现未安装开机计划任务。备份与日志长期保留，定期归档 `data/backups/` 和停止后的 `service.log`。

## 旧浏览器记录迁移

首次访问会检查当前浏览器原有 `ironspirit_wheel_v2` / `ironspirit_wheel_params_v4`。有已抽记录或异常缓存时先暂停该页面抽奖，显示迁移提示：

1. 先“导出旧缓存备份”，同时核对实物已领数量。
2. “迁移旧记录并继续”只允许服务当前奖池尚未开抽时导入。逐项核对 `deck + drawn = count`；不合格数据拒绝导入，不补签。
3. 旧记录没有时间，明确保留为未知；旧二等奖手办 5 份的等级原样保留，不把已中奖结果重新分级。
4. 原浏览器缓存保留；若核对后决定独立使用服务器奖池，可下载备份并点击相应按钮。此选择不会把旧抽奖记录加入服务器历史。

旧缓存按浏览器和域名隔离；Edge 的 localhost 缓存应先从 `http://localhost:5173/lucky-wheel.html` 迁移，127.0.0.1 的缓存从对应地址迁移。不要让另一个浏览器抢先开始新奖池抽奖，否则导入将拒绝覆盖已有记录。

新建奖池会生成输入数量的全新签数，历史保持可导出。用于下一场活动；如现场尚未结束，先核对实物剩余数量，不能凭满库存默认值重复发奖。

## 备份与恢复

管理奖池 → 展开，可下载全部 CSV 历史、备份数据库，也可 Ctrl+Shift+A。管理区只适合受控本机操作，没有公开网站账号体系。

数据库、WAL、备份与日志均位于 `data/`，已加入 Git 忽略。不能在服务运行时只复制主数据库文件，因为最近提交可能位于 WAL；使用页面备份按钮得到独立完整 SQLite 文件。

```powershell
# 验证备份、停止后台服务、保留恢复前的数据、恢复并重新启动
.\scripts\Restore-Backup.ps1 -Backup 'D:\实际备份路径\lottery-backup.sqlite'
```

若在前台启动服务，需先 Ctrl+C 停止。恢复脚本将原数据库和 WAL 保存到 `data/before-restore-时间/`，不会覆盖它们。恢复历史备份会把进度退回备份时刻；应先核对备份之后的实物发放，避免重新发放已经领取的奖品。

Git 只管理代码，回退代码不会自动回退库存。恢复数据通过 SQLite 备份完成。不要删除 `data/` 来“修复”服务，它会导致下次启动建立新奖池。

## 接口与本机边界

| 接口 | 用途 |
| --- | --- |
| `GET /api/health` | 服务状态 |
| `GET /api/state` | 当前奖池、剩余库存、最近 10 条结果 |
| `POST /api/draw` | `{requestId, campaignId}`，可重复提交相同编号取回原结果 |
| `GET /api/defaults` | 飞书文档默认配置 |
| `POST /api/campaigns` | 归档原池并创建新池，旧页面不能创建或抽取新池 |
| `POST /api/import-legacy` | 校验后导入旧浏览器记录 |
| `GET /api/export.csv` | 导出所有奖池结果，含来源与时间 |
| `POST /api/backup` | 在线备份并下载数据库 |

POST 要求 `Content-Type: application/json` 和 `X-Lottery-Client: local-wheel-v1`，浏览器请求必须同源。Host 仅允许本机 localhost 和 127.0.0.1，拒绝跨站请求。静态文件采用公开文件白名单，数据库、服务器代码和 `.git` 不对浏览器开放。

## 验证

`npm test`：校验文档库存、完整抽完、重复请求及重启、归档新池、失败回滚、旧记录导入与拒绝覆盖、在线备份恢复，以及两个独立服务进程同时处理 400 个请求（200 个不同编号各重复一次），总发放仍为 200。测试数据库与正式 `data/` 隔离。

页面验证使用另一个端口与 `output/lottery-checks/browser-data`，不消耗正式奖池。正式运行时网页会每 3 秒同步其他页面的库存；服务不可用时禁用抽奖，恢复后重新连接。
